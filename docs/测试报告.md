## 三、`npm run verify` —— 10 关可解性

**结果：通过（exit 0），✓ 全部检查通过**（10 关 × 10 项 + 汇总）

验证方式（`scripts/verify-levels.ts`）：

1. 用目标变换参数生成目标掩码，做 CPU 端 ASCII 预览；
2. 置为目标参数，计算与目标掩码的 IoU，必须 ≈ 1.0；
3. 施加「粗对齐（±0.12 世界单位 / ±5°）」与「精对齐（±0.05 / ±2°）」两档扰动，断言 `粗对齐 < 通关阈值 ≤ 精对齐`、`精对齐 ≥ 大师阈值`；
4. **离散控件可达性**：把目标吸附到玩家实际能摁出的最小粒度（位置 0.04、深度 0.1、角度 1°、旋转 5°、光源 0.1），所得 IoU 必须仍 ≥ 通关阈值；
5. 恢复初始状态，确认与目标有明显差异；
6. 校验深度合法性与目标是否贴边。

10 关目标状态 IoU **全部为 1.0000**，说明每一关都是可解的（解不出来就是程序 bug，不靠降阈值掩盖）。

**关于第 7–10 关阈值更低（0.67–0.70 vs 0.79–0.83）——这是几何性质，不是放水：**

初稿给四道花窗题目也配了 0.79–0.83 的阈值，`verify` 立刻报「精对齐 < 大师阈值」：实测精对齐只有
0.734–0.778。原因不是程序错，而是**细长棂条的轮廓对角度误差远比实心方块敏感**——方块只有四个角会偏，
而每一根细条整条都在偏，同样的 ±2° 会让 IoU 掉得更多。若强行把阈值留在 0.83，关卡**不可能通关**，
那才是真正的作弊。因此阈值按**实测可达性**重新标定，同时保持四条硬约束全部成立：

```
粗对齐 (0.473–0.534)  <  通关阈值 (0.67–0.70)  <  大师阈值 (0.72–0.76)  ≤  精对齐 (0.734–0.778)
离散控件可达 (0.938–0.964)  ≥  通关阈值
```

（"离散控件可达"是"玩家真的够得着"的硬保证：把目标吸附到玩家实际能摁出的最小粒度后，IoU 仍必须 ≥ 通关阈值；
它高于"精对齐"是因为吸附粒度 0.04 比精对齐扰动 0.05 更细。）

"孔洞数"不是目测的：`countHoles()` 用**四连通背景连通域计数**在掩码上真的数出来（第 7/8/9/10 关分别 2/4/9/12 个）。

**双路径比对为什么不用"凸包顶点序列"：** 第一版就是这么写的，结果第 10 关报不一致。逐项排查
（临时探针打印每个零件的 z 与去重后的 XY）确认**解析顶点完全正确**，差异只有 ~4e-8，
真正的两个原因是：(a) 挤出几何在端面三角化与侧壁处会输出**重复顶点**，解析式每个点只出现一次；
(b) 薄环扇块上常有三点近似共线，`convexHull` 的成员判定会在 1e-7 量级翻转。
这是**数值噪声而不是投影算错**，所以改成更贴切、更严格的写法：
`dedupePoints()` 后逐零件做**点集比对**（容差 1e-5），再叠加**整关掩码级 IoU ≥ 0.9995**。

### 6.4 自绘棂条的两个真实缺陷（[8c-4b] 分组，17 项）

这一组是**使用反馈驱动的回归测试**：用户报告"绘制棂条无法退出"并建议"选中节点要有明显标识、绘制过程要能看到预览"。
排查后发现是**两个真实缺陷**，而且此前 144 项 e2e 全部通过——因为旧的自绘测试走的是调试钩子
`workshop.drawPolyline()`（直接写文档），**根本没碰过绘制模式的界面路径**。

**缺陷一：进得去、出不来。** `onToggleDraw()` 的退出分支只调用了 `setDrawMode(false)`，漏掉了 `drawing.disable()`；
而 `finish()` 内部的 `cancel()` 只清空折线、**不改变 `enabled`**。于是绘制工具的闸门永久卡在打开状态：

| 症状 | 直接原因 |
|---|---|
| 按钮一直显示「结束绘制」，点了没有效果 | 按钮文案由 `state.drawing = drawing.isEnabled` 推导 |
| 点画布还会加点、但节点看不见 | `.stage` 的 pointerdown 监听仍在且 `enabled=true`，浮层却已被隐藏 |
| 窗格再也点不中，左键只能转视角 | `WorkshopController.hitTest()` 首句 `if (!this.entered \|\| this.drawing.isEnabled) return false` |

修法是**只保留一条退出路径** `exitDrawMode()`（`drawing.disable()` → `setDrawMode(false)` → 提示 → `render()`），
按钮与 Esc 都走它；Esc 同时改成渐进语义（折线上有节点 → 取消折线；折线为空 → 退出绘制模式）。

**缺陷二：预览代码一个像素都没显示。** 绘制浮层 `.draw-overlay` 是 `<svg>`，CSS 只写了 `position:absolute; inset:0`。
`<svg>` 是**替换元素**：`width:auto` 会退回内联默认尺寸 **300×150**（绝对定位下右/下 inset 被过约束忽略），
再加上 svg 根元素默认 `overflow:hidden`，画在窗格位置（远超 300×150）的节点与折线**全部被自己的 viewport 裁掉**。
所以"没有预览"不是样式不好看，而是一笔都没有真正画到屏幕上。
修法：显式 `width: 100%; height: 100%; overflow: visible`，并把"浮层矩形 == 画布矩形"写成断言（这类缺陷一旦回归是静默的）。

> 两个缺陷值得记的共同教训：**"有代码"不等于"有效果"，也不等于"能退出"。**
> 只要测试走的是调试钩子而不是用户路径，界面层的状态机与浮层几何就完全处于测试盲区。
> 因此本组 17 项全部用 `Input.dispatchMouseEvent` 真实鼠标事件驱动，落点也是先按悬停预览反查窗格坐标、
> 再排除被操作指引卡挡住的点，避免"点不上"伪装成"功能坏了"。

**"成对对照"那条断言为什么这么写**：同一套 29×29 采样点分别在绘制模式中与退出后各扫一次，
要求"绘制中可点中 = 0 且退出后可点中 > 0"。如果只断言后者，一个把 `hitTest` 写成恒 `true` 的错误实现也能通过。

**这一组抓出的两个问题**（都是先量出来、再改掉的）：

1. **三交六椀菱花的花心被一条门槛静默吞掉。** 首页最初沿用 `barWidth: 0.1`，
   而 `LiuwanLinghuaPattern` 里有 `if (r < barWidth * 1.2) break;` —— `r = 0.108 < 0.12`，

2. **探针读数撞上印章换字的 220ms 窗口。** 帧已切、章未换时立刻读 `.title-seal`，会读到**上一帧**的题名

> 这两条也说明：**"看到的现象"与"真实状态"之间常常隔着一个时间窗或一条阈值**，
> 断言必须落在稳定态，并且要能用数值（多边形数）而不是观感来确认。

3. **印章那条断言原先写成了"必须等于首帧的『步步锦』"，是一个时序陷阱。**
   轮播每 4.2 秒自动切换，页面一旦慢一点（实测：与另一个无头 Chrome 并发时）就已经切到第二扇，

   改成断言**不变式**：印章文本 == 当前 `.hero-frame.is-active` 那一帧对应指示点的 `aria-label`，
   并在印章换字动画（`.is-swapping`，淡出 220ms）结束后再读（最多重试 14×200ms）。
   这样它既能抓住"印章不跟随切换"的真 bug，也不会因为轮播走到第几帧而随机失败。
   **另一条推论：跑 e2e 时不要同时开别的无头浏览器**——它压的是 CPU，改的是页面计时。

### 6.6 关于"空白点环绕视角"那条断言为什么改过

`[3c]` 原本在画布内按固定比例网格找"不命中任何物体"的点作为拖动起点，实测选到 `(65, 60)`——
它确实没有物体，但**正落在顶部栏上**，鼠标事件被浮层吃掉，相机纹丝不动，报出"水平角 42.3° → 42.3°"的假失败。

修法是给这个搜索加上第二个必要条件：`document.elementFromPoint(x, y)` 必须**恰好返回画布本身**，
同时把候选点的 y 夹进"浮层之外"的安全区（`[150, innerHeight − 190]`）。
这与 `safeStagePoint()` 是同一类防护，只是这一次用在**选点**而不是**夹点**上。改后通过：
`(65, 196)` → 水平角 42.3° → 14.6°，俯仰角 8.0° → 29.1°。

### 6.7 关于墙体图层顺序，为什么不用像素采样

`[4b]` 断言的是 `renderOrder` 而不是"采样影子区域的像素颜色"。原因：物体位于相机与墙之间，**会遮住自己投在墙上的影子**，从默认机位根本采不到"影子压住描边"的像素（实测探针常采到 0 个影子像素）。而真正决定遮挡关系的就是 `renderOrder`（three 对共面透明对象的"按相机距离排序"在距离并列时结果不稳定），所以直接断言它才是可靠且可复现的。

### 6.8 字号放大后的版面复核（一次性探针，未进 e2e）

本轮把界面字号整体上调一档（正文改宋体后 10–12px 明显累眼），这类改动的风险不在"字号对不对"，
而在**连坐**：文字变大后原有固定宽高会折行或裁切。判断不能靠肉眼看截图，所以写了一次性 CDP 探针
（`.check/probe-type.mjs`，用完即删）遍历每个屏的**所有可见元素**，量三样东西：

1. **实际渲染字号直方图**（`getComputedStyle().fontSize`，不是读样式声明）；
2. **被裁掉的文字**：`scrollWidth - clientWidth > 1`（横向被压）或
   `scrollHeight - clientHeight > 1` 且 `overflow-y` 不是 `auto/scroll`（纵向真的看不到）；
3. 关键功能区的盒模型（侧栏宽 / 指引卡 / 状态条 / 输入框 / 滑块列宽）。

测得的关键数字：

| 视口 | 改前 | 改后 |
|---|---|---|
| 1440×900 · 被裁切处数 | 0（另有 4 处装饰层越界，属设计如此） | **0** |
| 1440×900 · 工坊字号分布 | 10×4 / 11×34 / **12×108** / 12.5×14 / 13×25 / 14×6 | 12×4 / 13×42 / **14×114** / 15×25 / 16×11 |
| 1440×900 · 工坊右栏滚动 | 2482px 内容 / 756px 可视 | 2649 / 747（列宽同步加宽后，比单纯放大字号的 2698 少 49px） |
| 1440×900 · 画布宽 | 852px | 812px（占 1416px 的 57%，仍是最大一块） |
| 1440×900 · 关卡页右面板滚动 | 953 / 900 | 920 / 900（面板 328 → 352px 后回到可视范围内） |
| 1180×820 · 被裁切处数 | — | **0** |
| 首页 `.title-main` 行盒 | `scrollHeight` 比 `clientHeight` 多 3px（82px 字被行盒切下沿） | 0（`line-height` 1.05 → 1.12） |

**"改前 0 处、改后仍 0 处"这条对照就是验收标准**：只要出现任何一处从 0 变成非 0，就说明
字号改大了但容器没跟上。探针不进 `e2e`——它依赖具体视口与文案，属于诊断工具而非回归断言；
真正稳定的回归由 `e2e` 里"浮层与画布同尺寸""可点中点数 > 0"这类**相对**断言承担。

**这个探针查不出的问题，被 e2e 查出来了**：探针只量"文字有没有被裁掉"，量不到
"浮层有没有盖住主体"。本轮把操作指引卡从 318px 加宽到 348px 后，
文字一处没裁、版面也好看，但**窗棂被盖住到"一个点都点不中"**——
`[8c-4b]` 的「退出绘制后窗格恢复可点选」立刻失败（详见第八节第 15 条）。
两个工具的分工因此很清楚：**探针管"读得到"，e2e 管"点得到"**。

## 八、开发过程中被测试抓到并修掉的真实缺陷

记录这些是为了说明"测试确实在起作用"，而不是走过场。

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | "相邻杆件交叉位置合并为实心" 失败 | 深度安全判断误用了**全局最浅深度**（`shallowestGap`）而不是**每根杆件各自**的深度，导致合法杆件被连坐跳过，墙上出现本不该有的空洞 | 两条投影路径都改为在循环内维护每根杆件自己的 `barGap`；并补了一条反断言"格心位置保持镂空" |
| 2 | "窗格与光源同深度" 失败 | 深度只是**接近**但合法时，也返回了"过于接近"的提示 | 从"全部杆件正常"的分支里移除该提示 |
| 3 | 回纹边饰笔画数不对（得到 28，期望 24） | `borderRepeat` 参数没有被加进 `clampPatternParameters()`，被夹回默认值 6 | 把 `borderRepeat` 纳入夹紧，并在 `PARAM_LIMITS` 里定义 `min/max/default` |
| 4 | "全部模板复杂度在上限内" 失败 | 文档建议的上限 320 低于最坏组合的实测值 324 | 按文档给出的区间上界调为 400，并把实测值打进断言详情 |
| 5 | 探针恒为 0（空断言风险） | 格心探针恰好落在步步锦的阶梯线上 | 改用格内归一化 `(0.35, 0.65)` 定位 + 5×5 采样 |
| 6 | e2e「撤销可以回退自绘」失败 | 测试按文本**包含**匹配按钮，"撤销"先命中了排在前面的"撤销节点" | 调试钩子的 `clickButton()` 改为**先精确匹配、再退回包含匹配** |
| 7 | e2e「越靠近光源投影越大」失败 | 断言里把 z=2.0 当成"贴近光源"（实际 z 越大才越贴近光源，光源在 z=14） | 改正断言方向并在注释里写明方向约定 |
| 8 | 生产后门检查误报 | 静态启发式按"出现位置必须在函数体内"判断，但函数上方的 JSDoc 也提到了该全局名 | 换成更强的断言：扫描整个 `src/`，只允许 `GameApp.ts` 提及该全局 |
| 9 | `TS6133: 'projectShape' is declared but its value is never read` | 引入 `projectParts()` 后 `projectShape()` 在全项目已无调用者 | 直接删除该导出（而不是加 `void` 或 eslint 忽略），并清理相关注释与导入 |
| 10 | verify-window「第 10 关 解析式投影与真实网格逐点一致」失败 | 临时探针逐项比对后确认**解析顶点完全正确**：原因是挤出几何在端面三角化与侧壁处会输出**重复顶点**，且薄环扇块上三点近似共线导致 `convexHull` 成员判定在 1e-7 量级翻转——是**数值噪声**不是投影算错 | 把断言改为"逐零件去重点集比对（容差 1e-5）+ 整关掩码级 IoU ≥ 0.9995"，语义更贴切也更严格 |
| 11 | 四道花窗题目「精对齐 ≥ 大师阈值」失败（0.768/0.762/0.734/0.779 vs 0.83） | 初稿沿用了几何关的 0.83 阈值。细长棂条的轮廓对角度误差远比实心方块敏感，同样的 ±2° 会掉更多 IoU——这是**新几何的真实性质**，不是 bug | 按实测精对齐重新标定阈值（见第三节），保持"粗对齐 < 通关 ≤ 可达"与"精对齐 ≥ 大师"两组硬约束成立；**不靠伪造 IoU 或跳过检查掩盖** |
| 12 | e2e「左键拖动空白处可环绕观看视角」失败（水平角不变） | 选点算法只保证"没命中物体"，选中的 `(65, 60)` 恰好落在顶部栏上，鼠标事件被浮层吃掉 | 搜索加上 `elementFromPoint(x, y) === canvas` 且夹进安全区 `[150, innerHeight − 190]`（见 6.3） |
| 13 | `workshop.css` 用旧朱砂覆盖了新配色 | 该文件后加载且自带一份 `:root`，把 `--cinnabar` 重新定义成更亮的 `#c2452d` | 删掉重复的 `:root`，色值统一由 `global.css` 提供；`--wood-soft` 补进全局令牌 |
| 14 | 首页的三交六椀菱花"只有三角格网、一片花心都没有"（肉眼看像"这张图本来就这样"） | `LiuwanLinghuaPattern` 有 `if (r < barWidth * 1.2) break;`，而首页沿用的 `barWidth: 0.1` 使 `r = 0.108 < 0.12`，**整片花心被静默跳过** | 改用与图鉴一致的默认尺寸（`barWidth: 0.09`）后 `r = 0.14`；并以**多边形数 50 → 360** 作为判据确认，而不是目视（见 6.5） |
